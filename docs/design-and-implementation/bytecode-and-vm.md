# Bytecode and the Virtual Machine

Bytecode is an intermediate representation; the virtual machine executes the bytecode instructions. Together they determine how Lua code runs.

## 1. Bytecode

Bytecode is a low-level intermediate representation produced by the Lua interpreter, closer to machine language than source code but still executed by the virtual machine. It is a sequence of instructions, each defining one operation for the VM to perform.

Three properties are worth noting. First, it is only weakly tied to the platform: bytecode format is defined uniformly by official Lua, and the same Lua version generates the same format on different platforms, but Lua explicitly states that precompiled binary chunks (files produced by `luac -o`) are not guaranteed to be portable across platforms. Machines that differ in byte order or in integer and float width may fail to load each other's chunks, so recompile on the target platform. Second, its structure is simpler and its operations clearer than source code, so the VM can parse and execute it more easily. Third, compilation performs some local optimizations, such as constant folding (`10 + 5` is computed as `15` at compile time).

The Lua interpreter generates bytecode during compilation: the compiler converts Lua source into bytecode for the VM to execute.

Use `luac -l -l` to inspect actual generated bytecode. For

```lua
-- source code
local a = 10 + 5
```

Lua 5.4 produces (excerpt):

```plaintext
main <t.lua:0,0> (3 instructions)
	1	[1]	VARARGPREP	0
	2	[1]	LOADI    	0 15     ; loads integer 15 into register 0 (local variable a)
	3	[1]	RETURN   	1 1 1	; 0 out
```

Two notes: `10 + 5` was constant-folded to `15` at compile time, so only one `LOADI` instruction is needed; register numbering starts at 0, so local variable `a` lives in register 0.

## 2. The Virtual Machine

The virtual machine is the engine that executes bytecode: it reads the bytecode instructions, decodes them, and runs the corresponding operations at runtime. It provides an abstract execution environment so that Lua programs can run on various platforms unmodified.

The VM uses a register model rather than the traditional stack model: registers hold operands and intermediate results. The instruction set is part of the bytecode and defines the supported operations, such as loading data, performing arithmetic, and calling functions. Memory management and garbage collection are also VM responsibilities.

Execution has four steps: load bytecode (from a file or from memory), decode the instructions one by one, execute the operation for each instruction type (arithmetic, function calls, and so on), and finally update register values, manage the function call stack and local variables, and perform allocation and reclamation.

Example:

```plaintext
-- bytecode example (local a = 10 + 5, actual Lua 5.4 output)
1	[1]	VARARGPREP	0          ; preparation for the main chunk
2	[1]	LOADI    	0 15       ; register 0 <- integer 15
3	[1]	RETURN   	1 1 1	; 0 out

-- how the virtual machine executes it
1. Load the bytecode (a binary chunk from luac -o, or a string compiled by load/require)
2. Execute VARARGPREP to finish preparing the main function's variadic arguments
3. Execute LOADI to write constant 15 into register 0 (local variable a)
4. Execute RETURN to return one value and finish
```

## Summary

Bytecode defines the program's operations; the VM decodes and executes these instructions and also owns memory management and garbage collection. Understanding this pipeline gives a basis for investigating performance problems and debugging bytecode.
